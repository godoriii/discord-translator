# 설계 과제: 디스코드 웹 인라인 번역 유저스크립트 (용어집 내장)

## 목표
Chrome + Tampermonkey 유저스크립트. discord.com/app(웹 디스코드)의 채팅 메시지를 실시간으로 감지해 Claude API로 한국어 번역하고, 각 메시지 원문 바로 아래에 번역문을 인라인 삽입한다(이중언어 표시). Windows/Mac 양쪽 Chrome에서 동일 스크립트 한 벌로 동작해야 하며, GitHub raw URL로 호스팅해 @updateURL/@downloadURL 자동 업데이트를 쓴다.

핵심 차별점: **사용자 관리 용어집(glossary)**. 예: WoW 스킬/지명/보스 영어→한국어 공식 명칭("Kill Command"→"살상 명령", "Mongoose Fury"→"살쾡이의 격노", "The Venomous Abyss"→"맹독 심연"). 용어집은 별도 JSON으로 GitHub에 두고 스크립트가 fetch(로컬 오버라이드/추가 항목도 지원). 일부 항목은 "미확정(†)" 표시가 필요할 수 있다. 용어집은 처음 수십~수백 개, 최대 수천 개까지 커질 수 있다.

## 제약
- 디스코드 API/봇/클라이언트 모드(BetterDiscord 등) 사용 금지. DOM 읽기 + 표시용 노드 삽입만 허용(디스코드 서버로 전송하는 것 없음).
- Claude API 호출은 GM_xmlhttpRequest(CORS 우회)로 직접. API 키는 GM_setValue 저장(스크립트 파일에 절대 포함 안 함). 모델명/타깃 언어/용어집 URL/자동번역 on-off 등은 설정 패널에서 변경.
- 디스코드 DOM은 클래스명이 해시로 난독화되어 있고 메시지 리스트는 가상화(virtualized)되어 스크롤 시 노드가 재마운트된다. 안정적 훅은 `id^="message-content-"`, `li[id^="chat-messages-"]`, `[data-list-id="chat-messages"]`, `[role="article"]` 같은 id/data/role 속성으로 추정됨(검증 필요).
- 보존해야 할 것: 멘션(@user, #channel), 커스텀 이모지, 링크, 코드블록/인라인코드, 스포일러, 인용. 임베드(embed)/첨부 캡션도 가능하면 번역.
- 이미 한국어인 메시지, 이모지만/링크만/빈 메시지는 API 호출 없이 스킵.
- 편집된 메시지(내용 변경) 재번역, 삭제 메시지 처리, 채널 전환 시 처리.
- 비용/지연: 새 메시지가 짧은 시간에 여러 개 오면 한 번의 API 호출로 배치. 메시지 id 기준 번역 캐시(메모리 + GM storage, 크기 상한). 429/5xx 백오프. 동시 요청 수 제한.
- 과거 메시지로 스크롤 올릴 때 수백 개를 한꺼번에 번역해 폭주하지 않아야 함(뷰포트 기준/수동 트리거 등 정책 결정 필요).
- UI: 번역문은 원문 아래 회색 톤 작은 글씨 블록, 로딩 표시, 실패 시 재시도 버튼, 전체 토글 단축키(예: Alt+T), 메시지별 "원문만/번역만" 토글은 선택. Tampermonkey 메뉴(GM_registerMenuCommand)에서 설정 열기.
- 단일 파일 유저스크립트(대략 500~900줄, 순수 JS, 빌드 도구 없음). 별도 `glossary.json`. 로그인 없이 검증할 수 있도록 디스코드 DOM 구조를 흉내낸 로컬 테스트 하네스(HTML + GM_* 심 + 가짜 API 응답 모드)도 함께 만든다.

## 결정이 필요한 설계 질문 (각각 추천안 + 근거 + 기각안 이유)
1. DOM 감지 전략: MutationObserver 범위/필터, 가상화 리스트에서 중복 삽입 방지, 재마운트 시 캐시로 즉시 복원하는 방법, 메시지 텍스트 추출 방법(textContent vs innerText vs 노드 워킹으로 멘션/이모지 토큰화).
2. 용어집 적용 전략: (a) 전체 용어집을 system prompt에 넣고 prompt caching(cache_control ephemeral)으로 비용 절감, (b) 메시지마다 매칭된 용어만 골라 프롬프트에 주입, (c) 사전 치환(placeholder) 후 번역, (d) a+b 하이브리드. 용어집이 수천 개로 커질 때의 전환 기준. 매칭 알고리즘(대소문자, 복수형/소유격, 다단어 용어, 부분일치 방지). 미확정(†) 용어의 표시 방법.
3. 배치/동시성: 디바운스 윈도(ms), 배치 최대 개수, 요청 포맷(번호 매긴 메시지 → 같은 번호의 JSON 배열 응답), 응답 파싱 실패 시 복구, 부분 실패 처리.
4. 스크롤업 과거 메시지 정책: 자동 전부 vs 뷰포트만(IntersectionObserver) vs 수동 버튼 — 추천안.
5. 실패 모드 목록과 완화책(디스코드 DOM 변경, API 키 만료, 레이트리밋, 번역 순서 뒤섞임, 언어 감지 오판, 매우 긴 메시지, 코드블록만 있는 메시지 등).
6. 코드 구조: 단일 파일 내 모듈 분할(섹션/네임스페이스), 상태 저장 스키마(GM storage 키 목록), 설정 기본값, 테스트 하네스 설계(가짜 DOM에서 시나리오: 신규 메시지 유입/스크롤 재마운트/편집/채널 전환/한국어 스킵/배치/실패 재시도).
7. 프롬프트 설계: system prompt 원문(한국어 번역가 역할, 용어집 강제 규칙, 게이머 채팅 톤, 멘션/이모지/링크 보존 규칙, 출력 JSON 스키마), 사용자 메시지 포맷. 번역 품질을 위해 직전 N개 메시지 문맥을 함께 보낼지 여부.

## 산출물 형식
Sonnet급 구현 워커가 추가 결정 없이 그대로 구현할 수 있는 **구현 지시서**: 파일 목록, 각 모듈의 함수 시그니처와 책임, 데이터 구조/저장 키, 상수 기본값, 프롬프트 전문, 엣지케이스 처리 표, 테스트 하네스 시나리오 목록. Claude API 요청 바디의 정확한 필드명은 워커에게 별도로 제공하므로 "system prompt에 cache_control을 둔다" 수준으로만 적어도 된다. 장황한 배경 설명 대신 결정과 근거를 간결하게.
